### 2026-11-19 — Proposal warna semantik (token tema) vs hex tetap pada `mark color`/`highlight` dan frame `"none"`
- Task: Spike S2 (butir 15) / `docs/data-format.md` §5.4, `docs/spec-canvas.md` §6.4 (`FR-CVS-05`), `docs/spec-ui-nfr.md` §7.4 & §8.1
- Bukti kontras terhitung di Spike S2 (`S2_CONTRAST_RATIOS`, WCAG 2.1 rasio luminance relatif dari `getComputedStyle`):
  - **Mode dark (`card` `#11151d` / `frame: "none"` `rgb(20, 20, 20)`):** `Auto` (`#e6e9f0`) = `15.04–15.16:1`, 5 swatch hex (`#7c9cff`, `#fbbf24`, `#34d399`, `#f87171`, `#a78bfa`) = `6.61–11.04:1` (**lulus AA ≥ 4.5:1**), namun `Highlight` (`#fbbf24`) dengan teks warisan `#e6e9f0` = **`1.37:1` (gagal berat)**.
  - **Mode light (`card` `#ffffff` / `frame: "none"` `--bg: #f6f8fc`):** `Auto` (`#0f172a`) = `16.79–17.85:1`, `Highlight` (`#fbbf24` + `#0f172a`) = `10.69:1` (**lulus AA**), tetapi ke-5 swatch hex dari palet dark semuanya gagal AA (**`1.67–2.77:1`** pada `card`; **`1.57–2.60:1`** pada `frame: "none"`).
  - **Batas matematis:** Tidak ada satu pun nilai hex tetap `#rrggbb` yang dapat sekaligus mencapai rasio ≥ `4.5:1` terhadap `#ffffff` (`L=1.0`, mensyaratkan `L_fg <= 0.1833`) dan `#11151d` (`L=0.0079`, mensyaratkan `L_fg >= 0.2105`).
- Opsi yang dipertimbangkan:
  1. **Warna semantik berbasis token tema (mis. `token:accent`, `token:warning`, `token:success`, `token:danger`, `token:violet`):** otomatis menyelesaikan ke palet dark/light dengan kontras AA pada kotak standar (`--card`) maupun kotak ber-**frame `"none"` (`style.bg: null`, `border: null`)** yang teksnya langsung duduk di atas kanvas `--bg`. **Dampak ke `data-format.md` §5.4 & skema:** membutuhkan perluasan whitelist `textStyle.color` dan `highlight.color` (yang saat ini hanya menerima `#rrggbb`) untuk menerima token bernama (atau kenaikan `schema` v1 -> v2 + migrasi), serta penanganan khusus bila pengguna memakai `style.bg` hex custom tetap (mis. kartu kuning terang pada mode dark sehingga token teks terang gagal kontras di atas kartu custom tersebut).
  2. **Hex tetap `#rrggbb` sesuai `data-format.md` §5.4 & `FR-CVS-05`:** tidak perlu mengubah skema v1; saat memilih di palet UI, swatch memetakan warna sesuai tema aktif saat itu (mis. `--branch-1..8` versi light atau dark ke hex), dan `Auto` (`color: null`) tetap menjadi default yang mewarisi `var(--fg)`. **Konsekuensi:** dokumen yang dibuat dengan swatch hex pada satu tema akan turun kontrasnya bila dibuka di tema sebaliknya—terutama terlihat pada **frame `"none"`** (`style.bg: null`) karena latar ikut berpindah antara `#0b0e14` dan `#f6f8fc`—kecuali renderer menerapkan penyesuaian kontras saat `style.bg === null` atau hanya mempertahankan penyorot bertint transparan/pair teks gelap pada `highlight`.
- Keputusan sementara (opsi paling sederhana): Jangan ubah `src/domain/schema` pada S2; catat kebutuhan memilih **Opsi 1 vs Opsi 2 (+ aturan pasangan warna `highlight` di dark mode)** sebelum implementasi M4 (`FR-CVS-05` / `FR-TXT-01`).
- Perlu keputusan pemilik: **ya** (sebelum M4).

### 2026-11-18 — Detail `buildTree`, `changeset`, dan fallback `order` (`T1.3`)
- Task: T1.3 / `data-format.md` §5.1 & §5.3, `spec-nodes-search.md` §6.7 (FR-NODE-01..05)
- Masalah atau ambiguitas:
  1. Bagaimana `buildTree` menangani folder tanpa parent `node.json` (orphan), folder berslug terlarang, serta ID untuk node `corrupt` yang mungkin tidak punya ULID valid?
  2. Bagaimana `moveNode` memodelkan `node.json` milik akar subtree yang dipindah (karena `order` dan `updatedAt` berubah) bersama file lain yang isinya tetap?
  3. Bagaimana `reorderNode` menangani dua sibling yang `order`-nya seri (`prevOrder === nextOrder`) atau mengandung key tak valid untuk `fractional-indexing`?
- Opsi yang dipertimbangkan:
  1. Membuang/mengabaikan orphan & node terlarang dengan `TreeIssue` tanpa menyentuh file, atau membuat node virtual.
  2. Memasukkan `node.json` akar subtree ke `deletes` + `upserts`, atau memodelkan seluruh file subtree di `moves` (`{from, to}`) + `upserts` untuk `${newPath}/node.json` yang berubah.
- Keputusan sementara (opsi paling sederhana):
  1. Folder berslug terlarang atau tanpa parent `node.json` diabaikan dengan `TreeIssue` (menjaga konsistensi `path === parent.path + '/' + slug` tanpa mengubah folder tak dikenal). Node `corrupt` / `newer-schema` mendapat ID read-only deterministik `__corrupt__:<path>`, tetap mengklaim `slug` foldernya agar tidak tertimpa sibling baru, dan diblokir dari semua operasi tulis (termasuk operasi `moveNode` dan `deleteNode` pada induknya).
  2. `moveNode` mencatat seluruh file subtree (termasuk aset yatim di `assets/` maupun file tak dikenal via `extraFiles`) di `changeset.moves` (`{ from, to }`), `deletes: []`, dan hanya `${newPath}/node.json` di `changeset.upserts` (semantik urutan applier: `deletes` -> `moves` -> `upserts`, sehingga isi `upserts` menang atas hasil `moves`). Karena `domain/` murni tanpa IO repositori atau filesystem, daftar file per node (`assets` dan `extraFiles`) dipasok oleh pemanggil (`storage/` atau `sync/` saat memindai pohon file) melalui `TreeBuildEntry` ke `buildTree`.
  3. `generateOrderBetween` membungkus `fractional-indexing` dalam `try/catch`, memvalidasi batas ketat `a < key < b`, dan memakai fallback leksikografis deterministik bila key input tidak valid. Jika target posisi di `reorderNode` diapit dua sibling ber-`order` identik (`prevOrder >= nextOrder`, mis. akibat node `corrupt` ber-order fallback `'a0'`), `reorderNode` menolak dengan `reason: 'order_collision'` alih-alih memberi `order` yang sama atau mengubah `node.json` tetangga.
- Perlu keputusan pemilik: tidak

- **2026-11-19 (T2.2 / M2 Review) — Kebijakan kegagalan tulis IndexedDB (`storageError`), bentrok path Undo, induk dipindah/dihapus saat Undo, dan `getEffectiveDeletes`:**
  1. Saat penulisan ke IndexedDB gagal, perubahan yang memicu kegagalan tetap dipertahankan di memori (`hasUnsavedChanges: true`, `storageError` aktif) dan seluruh mutasi berikutnya diblokir (`reason: 'storage_error'`) hingga pengguna menekan tombol Retry dan penyimpanan berhasil — sehingga `Changeset` baru tidak pernah dihitung dari state memori yang menyimpang dari IndexedDB.
  2. Selama jendela Undo 10 detik, mutasi non-hapus (seperti membuat node baru) diizinkan tanpa mematikan jendela Undo. Bila node baru dibuat pada `path` yang sama lalu pengguna menekan Undo, `restoreSoftDeletedSubtree` memberi slug unik baru (`resolveUniqueSlug`, mis. `pwn-2`) dan memperbarui path subtree yang dipulihkan (`dirty: 1`) agar tidak pernah ada dua node aktif di satu `path` dan tidak ada data yang hilang.
  3. Bila induk node yang di-soft-delete **masih ada menurut ID** (meski path induk berubah karena dipindah/rename) lalu pengguna menekan Undo, `restoreSoftDeletedSubtree` memulihkan subtree **di bawah induk tersebut pada path barunya**; node hanya dipromosikan ke **root (`parentId: null`)** dengan slug unik bila induknya memang sudah tidak ada. Fungsi mengembalikan `RestoreSoftDeleteResult` agar UI (`AppShell`) dapat menampilkan toast lokasi pemulihan, dan toast Undo lama langsung ditutup ketika penghapusan berikutnya memfinalisasinya.
  4. Kolom `basePath` pada `nodes`, `canvases`, dan `assets` menyimpan path ter-sync terakhir (`baseBlobSha` non-null) dan tetap dipertahankan saat pindah atau Undo yang mengubah path, sementara path remote lama dicatat ke `pendingDeletes`. `finalizeSoftDeletes` mencatat seluruh path lama ke `pendingDeletes`; `getEffectiveDeletes` di layer `storage/` menghitung `pendingDeletes` dikurangi path aktif pada state akhir untuk dipakai sync.
